# 2026-07-26

## 今日の結論

> **「BC は容量の壁」という前提が誤りだったと判明し、学習レーンが一度開いた。しかし出荷段階で
> 2026-07-09 に潰したはずの地雷（sandbox の numpy）を踏み直し、v042 が ERROR。原因を確定させて
> numpy-free で再提出（v043, 検証通過）。ただし出せる構成は強さのゲートに落ちており、
> 「伸びた分は出せない／出せる分は伸びていない」という板挟みが今日の正味の位置。**

## 1. 前提の誤りを見つけた: BC は「容量の壁」ではなく「投資不足」だった

07-24 に学習レーンを「24ネガティブで確定的に終了」と結論したが、その根拠になった BC ネットを
`results/pre_grimm10/history.json` で確認したところ:

- **d_model=128 / encoder1層+decoder1層 / 2ヘッド を、147秒 × 3 epoch = 合計約7分**しか学習していない
- held-out top-1 は **0.6023 → 0.6121 → 0.6240 と最終 epoch でも上昇中＝未収束**

つまり「忠実度の壁」はこの7分の実行から導かれた結論だった。GPU は遊休、教師コーパス
（**1,083,793 決定 / 12,235 試合 / 10日**）は既存＝**データ作成コストゼロで検証できる**。
ユーザー方針「遊休計算資源でハイリスク・ハイリターンを試し、良い結果の時だけ採択」に合致するため
exp083 として着手した。

## 2. スケールアップは2度失敗し、真因は「容量」でなく「最適化」だった

パイプラインは 1層・d128 専用にハードコードされていたので、まず可変化した
（`pretrain.py` に `--heads/--enc-layers/--dec-layers/--d-ff/--warmup-steps/--clip/--cosine`、
`arch.json` 出力。`npnet.py` の numpy 推論を層ループ化。回帰パリティ 500/500・多層 60/60 で確認）。

| 構成 | ep0 | 経過 |
|---|---|---|
| A: d256/2+2, lr 3e-4, warmup なし | 0.4095 | 0.586 で頭打ち（baseline 0.624 に届かず） |
| A2: 同 + warmup 4000 | **0.5740** | ep1/ep2 で 0.4896/0.5222 と振動 |
| 探査: lr 1e-4 + warmup + clip（定数LR, 3ep） | 0.6077 | **ep1 で 0.6255＝baseline 最終値を超え安定** |
| **A3: 探査レシピ + cosine, 24 epoch** | 0.6053 | **ep23 0.6892（最後の6epochが平坦＝収束）** |

**公式サンプルの lr 3e-4 は d128/1+1 には適切だが d256/2+2 には高すぎた**。同一アーキ・同一データで
warmup を入れるだけで ep0 が +0.165 動いたことで、容量ではなく最適化不全だと確定した。
2時間の賭けを繰り返さず**15分の LR 探査で切り分けた**のが効いた。

結果: top-1 **0.6238 → 0.6892**、ラダー最大の穴だった **Alakazam 戦が最も伸びた（0.6267 → 0.7059）**。
対旧ネット（同一デッキ・席交替・n=200）で **0.665（133-66-1, z=+4.67）**＝事前登録した3ゲート全通過。

## 3. v042 が ERROR — 原因を確定させた

提出 54987775 が `"Validation Episode failed."`。検証エピソード 88157662 を取得して診断:

- `statuses: ["ERROR","ERROR"]`、steps は2つだけ（step0 初期化 → step1 で両者エラー）
- **`remainingOverageTime` 600 → 598.674 ＝ エージェント時間の消費はわずか 1.33秒**

**タイムアウトではなく、起動直後のプロセス即死**。`try: import numpy` で包んだフォールバック設計は
無力だった——ネイティブ拡張の abort や OOM kill は例外にならないので握りつぶせない。

そして**同じ文言・同じ失敗クラスが v015（2026-07-09）で既に起きていた**。当時の結論は
`npmcts_policy.py` と `export_pure.py` のヘッダに残っている:

> 「cg が numpy に依存しているから sandbox にも numpy がある」という仮定は一度も検証されておらず、
> この crash によって反証された。

当時は `__file__` 問題と numpy を同時に直したため numpy 単独の有罪は未確定だった。今回
**`__file__` を完全に排した v042 が同じ文言で落ちた**ことで、残る差分（**numpy 経路 / 148.5MB という
桁違いのサイズ**）に原因が絞られた。v043 が `npmcts_policy.py` バイト同一・numpy の有無とサイズだけ
違う構成で**検証を通過した**ので、実地で裏が取れた。

- 実害は無し。**ERROR 提出は eligible に入らない**（LB は v041 のまま維持されていた）。
- 恒久メモリに記録: [[sandbox-no-numpy]]。

**教訓**: ローカルの `sandbox_replica.py` は「numpy がある環境」しか再現できず、この失敗を
**構造的に検出できない**。緑のローカル検証は根拠にならなかった。v015 で獲得した制約を、
検証したつもりで踏み越えたのが敗因。

## 4. 対照実験で板挟みが確定した（誠実なネガティブ）

d128/1+1 を A3 と同じ良いレシピで 24 epoch 再学習（`sc083_d128ctl`）。目的は「伸びは容量か学習量か」。

| | 旧 d128（7分） | d128ctl（2時間） | A3 d256/2+2（2時間） |
|---|---|---|---|
| top-1 (oracle-free) | 0.6238 | **0.6577** | **0.6892** |
| vs Alakazam | 0.6267 | 0.6745 | 0.7059 |
| **対旧ネット n=200（ゲート2）** | — | **0.525 (z=+0.71) FLAT** | **0.665 (z=+4.67) PASS** |

**学習量は top-1 を +0.034 上げたが、強さには変換されなかった**。A3 の利得のうち実際に打ち筋の
強さになったのは容量側。＝「純Python の小型モデルで同じ性能」という都合の良い出口は**存在しない**。

そして出荷可能性が逆向きに効く:

- **出せる構成（numpy不要の d128）はゲート2 に落ちる**（0.525）。旧同級は実ラダー 0.43 だった。
- **ゲート2 を通る構成（A3）は出せない**。純Python換算 ~0.7s/act（numpy比 3.7倍から推定）＝
  ゲート3（≤0.3s）超過で、v015 が 2.3s/act で実失敗した領域に近い。重みも純Python形式で ~110MB。

## 5. v043 提出（ゲート不合格を承知の実測、ユーザー判断）

ゲート2 不合格を報告した上でユーザーが「実ラダーで測る」を選択。

- `build_pure/`（**47.9MB**、numpy 完全排除、`npmcts_policy.py` バイト同一、d128/h2/1+1）
- 検証: torch↔出荷純Python パリティ n=300 argmax **300/300**（max|dp|=1.24e-05）、
  スモーク 120試合 **0エラー**、sandbox replica（bare exec・`__file__`なし）144手 **max_act 0.29s**
- **sub 54988388 = COMPLETE**（検証通過）。**v040 koff (845.4) を退出**
- eligible = **{v043 BC-d128ctl, v041 alakazam}**

**判定基準（事前登録・変更しない）**: 実ラダー ~40試合の勝率が **koff/alakazam の 0.54 を超えること**。
超えなければ即座に実績ビルドへ復帰し、学習レーンを誠実なネガティブとして再度閉じる。
旧 d128 級は 0.43 だった＝**事前確率は低い**と明記しておく。
