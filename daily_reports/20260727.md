## 2. 【重要】手番時間の制約を誤解していた

disc729219 でホスト回答が引用されていた:

> Each team has **600 seconds TOTAL for the entire game**. There is **no per turn increment**.
> CPU only, **1.6 vCPUs, 8GB RAM**.

自分たちのラダー・リプレイで裏を取った（`remainingOverageTime` の消費）:

```
実測4試合:  52.3s / 14.6s / 10.1s / 40.1s   （いずれも 600s 中）
→ 最悪でも 600秒中 52秒 ＝ 余裕は約11倍
```

**私が置いていた「≤0.3秒/手」というゲートは、v015 の失敗を「2.3秒/手が遅すぎたため」と
推定した仮説に基づいていた。しかし v015 の真因はその後 `__file__` 未定義と判明しており
（v015-fix4）、速度仮説は否定されずに残っただけだった。** それを制約として扱い続けた結果、
昨日測定した最大のレバーを「予算外」として棚上げしていた。

```
探索 sc16 の効果:   0.733 (z=+3.61)   ← 昨日のどのネットワーク改善より大きい
推定コスト:  ~1.25秒/手 × ~108手 = 135秒   （予算600秒、1.6vCPU で2倍遅くても 270秒）
```

## 4. exp083d: 探索の出荷実装（進行中）

`SEARCH_COUNT` を固定値でなく**適応制御**にした。観測に含まれる `remainingOverageTime`
（＝残り予算）を読み、実測コストから1手あたりの上限を自己計算する:

- 起動直後は推定値がないので上限 sc16 で走り、3手で自己較正
- 残り予算 120秒を切ったら探索停止（生 argmax に縮退）
- 最後の60秒は予約（使い切らない）
- ストライク判定も「1.5秒/手」から「1手で30秒」に変更（予算が実際の制約なので）

**開発機の実測値を信じず、サンドボックスの実速度（1.6 vCPU）に合わせて自動調整する**設計。
