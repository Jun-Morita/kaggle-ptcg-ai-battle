## 1. 探索の A/B — 採用せず

`search.py`（検証付き上書き）を実装し、価値モデル（80万行、AUC 0.9086）と組み合わせて測定。

```
閾値 0.02   n=60    探索なし 0.567 / 探索あり 0.467   -0.100 (z -1.10)  上書き 10.8%
閾値 0.12   n=120   探索なし 0.608 / 探索あり 0.542   -0.067 (z -1.03)  上書き  5.1%
```

**上書き率を半減させても改善しない**＝上書きが多すぎるのではなく、上書きの選び方が良くない。

原因は価値モデルと考える。AUC 0.9086 は全局面での数字で、終盤が簡単なだけ。探索が必要と
するのは**同じターン内の兄弟局面の順序**で、そこでは差が小さくノイズに埋もれる。学習分布の
偏り（負けの行がミラー戦に偏る、互角局面も勝ちラベル）もこの用途には効いている。

正しく直すには価値の学習方法を変える必要がある（局面の優劣を直接学ぶ、自己対戦で作る）。
締切まで9日でそこに賭けるのは合わないと判断し、レーンを閉じる。

### 途中で出した符号バグ（記録）

最初の測定は **0.015（3-197）** という壊滅的な数字だった。原因は `search.py` に自分で
書いたコメントの通り:

```python
# the evaluated position is scored from the seat to move; ...
# so flip when the position is the opponent's to play
return v      # ← 反転を書いていない
```

`_greedy_finish` は自ターン終了時点で止まるので評価対象は**相手の手番**。`base_state` は
手番側視点なので、探索は**相手の勝率を最大化する手**を選んでいた。今日4件目の
「静かに劣化する不具合」だが、前3件と違い**大きく壊れたので即座に分かった**。
危ないのはもっともらしい数字を出す壊れ方の方。

## 2. v5（特性の発動前提を特徴量に）— 却下

Munkidori の過剰使用 3,137件に対して、engine API から計算できる前提を8個追加した
（318 → 326 特徴量）。

```
局面側  own_movable_counters / opp_active_counters_to_ko / move3_would_ko
        own_dark_energy_total
選択肢側 opt_src_dark_energy / opt_src_energy_n
        opt_tgt_energy_need / opt_tgt_need_after
```

Adrena-Brain は「この ポケモン に {D} エネルギーがついていれば、自分のポケモンから
ダメージカウンターを最大3個、相手のポケモンに移す」。**D エネの有無も、移せるカウンターが
あるかも、移して倒せるかも、モデルには見えていなかった。**

教師データの 3.3% で `move3_would_ko` が成立しており、情報としては実在する。
教師再現も 0.7616 → 0.7636 と微増した。だが**直接対決で v4b に負けた**ので採用しない。
