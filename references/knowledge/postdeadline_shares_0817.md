## 2. hosikusa — 遺伝的アルゴリズムでデッキとスコアを同時最適化

- 出典: `hosikusa/optimization-of-deck-and-agent-scores-using-a-gene`（Kaggle notebook, 08-17）

### 要点

```
設計変数  デッキ        カードIDごとに [初期枚数, 下限, 上限]
          エージェント   スコアパラメータ38個 × [初期値, 現在値, 下限, 上限, 刻み]
目的関数  ローカル対戦の勝利数
手法      遺伝的アルゴリズム
成果物    best_individual.json（最良のデッキ + スコアの組）
```

デッキの枚数構成とルールベース方策の重みを、**同一の探索空間に置いて同時に最適化**する。

### 使える場面

**我々が一度も試さなかった路線であり、今回の最大の敗因に直結する。**

我々はデッキを「上位プレイヤーから複製するもの」として固定し、方策だけを模倣学習で
磨いた。結果:

- 我々の Grimmsnarl は最終的にフィールドに対し勝率 **0.33**（実測、n=1155）
- dragapult 0.341 / ex_beatdown 0.193 に対し、この2デッキがフィールドの **61.5%**
- 複製した他デッキ5種はどれも操れず（同じ7相手で我々 0.7181 対 最良クローン 0.5418）
- 原因はデータ量ではない（同じ決定数で main top-k 0.7096 対 0.5841）。
  **特徴量が単一アーキタイプに癒着していた**

つまり「デッキを固定して方策だけを磨く」という構造そのものに限界があった。
デッキを設計変数に含める設計は、この限界を最初から回避している。

### リスク・注意

- 目的関数が「ローカル対戦の勝利数」。**我々が踏んだのと同じ罠**（ローカル評価が
  実ラダーを予測しない）を踏んでいる可能性がある。最終順位で有効性を確認すること。
- 対象がルールベースのスコアパラメータ38個。我々の GBDT 方策（数千本の木）には
  そのままでは適用できない。デッキ側の最適化だけを取り出すか、
  方策側を少数パラメータで表現し直す必要がある。

## 4. Abhyuday — Internal Tooling / Master Control Plane

- 出典: <https://www.kaggle.com/competitions/pokemon-tcg-ai-battle/discussion/735649>（08-17、v18/c8）
- 著者は top 30 到達を明言。取得日 2026-08-18。

### 構成

```
Local Leaderboard    全ボットの強さを1本の記録で管理。arena で試合が起きるたび更新
Arena                任意数のボットで総当たり。8コアを常時割り当て動的マッチング
                     「いま最強はどれか」を継続的に答える
Submission analytics 提出後30分で実ラダー ELO を ±30 で推定
                     どのデッキに負けているか / 負け方（デッキアウト・接戦・完敗）
                     / 高ELO帯で苦戦か特定マッチアップか / まだ登っているか
Meta Analysis        クロスデッキ勝率行列。メタ回転を検知して警告
Playground           人間が自分のボットと対戦。attention・着手確率・勝率推定を可視化
```

構築に1日、節約できたのは数週間と本人が記述。

### 我々との決定的な差

**評価の較正方法。**

| | 我々 | Abhyuday |
|---|---|---|
| 方式 | 固定6セルの対メタプール重み付き勝率 | 多数ボットの総当たり arena で相対 ELO |
| 相手 | 固定（我々が作ったクローン＋公開エージェント） | ボットが増えるたびに増える |
| 系統誤差 | **相手が実物とずれても検出できない** | 総当たりなので較正が効く |
| 実 ELO 推定 | できない（ゲート順位とラダー順位が逆転） | 提出後30分で ±30 |

我々のゲートは全セルで実ラダーを過大評価していた（dragapult 0.865 対 実測 0.341, n=264 /
mixed_ex1 0.864 対 0.421, n=183 / ex_beatdown はセルすら無し、フィールドの27.3%）。
**固定相手だと系統誤差が全候補に等しく乗り、誤差の存在自体が観測できない。**
較正に使えるラダー標本が n=4〜14 しかなく、1週間気づけなかった。

### 弱点マッチアップの潰し方（コメントより）

> Q: 900帯のエージェントに負けていると分かったとき、どう直すのか
> A: たいていは特定のデッキに対する不足。**そのデッキを回せる強く多様な教師を作って、
>    自分のエージェントの対戦相手に加える。**最も成功した例が dragapult で **25% → 70%**。

さらに、その勝率は**カリキュラムの動的設定に使用**（リプレイ自体は学習に使っていない）。

**我々が届かなかったのはここ。**

```
我々        dragapult 実測 0.341（n=264、フィールドの34.2%）
            クローン build_drg は全対戦相手に負けるほど弱く、練習相手にならない
            コーパス内の dragapult 戦は 4.4%、行重み3倍でも埋まらず
            （x4b3 は実ラダーで dragapult 0-4）
Abhyuday    強く多様な dragapult 教師を「作って」対戦相手に加え 25% → 70%
```

差は **「任意のデッキの強いボットを自分で生成できるか」。**模倣学習は教師を既存
リプレイからしか得られない。self-play / RL 側はそれができる。hosikusa の GA
（デッキと方策を同一探索空間で最適化）も同じ前提に立っている。

### メタ回転は「検知」ではなく「対応手段」が問題だった

> Meta Analysis が dragapult メタの台頭を検知して警告。**2日の猶予**ができたので
> 対策を学習させ、最終的に対 dragapult 70%。

我々もメタ回転は日次で追えていた（08-11 時点で dragapult 18.9% を把握）。
**検知はできていて、打てる手が「行重みを3倍にする」しか無かった。**

### 結論（本人の言葉）

> 早い段階で堅牢で使いやすいツールに投資すること。**なぜ負けているか分からなければ
> 改善はできない。**

## 12. Anil Ozturk — 最後の1週間で Dragapult BC + RL + MCTS

- 出典: <https://www.kaggle.com/competitions/pokemon-tcg-ai-battle/discussion/736121>（08-19）
- 到達: 上位ブロンズ〜下位シルバー。参加は最終週のみ。

### (a) デッキ選択 — 我々と同一の入口、逆の分岐

> I first put most of my work into the **Grimmsnarl** deck. It had the largest
> quantity of replay data (~1.3M decisions).
> Examined the replays of the top 12 teams. **9 of the 12 top teams played
> Dragapult.** Dragapult was 40 percent of their games. **Switched to the deck.**

Grimmsnarl を選んだ理由（リプレイ量が最大）は我々と完全に同一で、決定数も近い
（彼 1.3M / 我々 1.4M）。**違いは上位12チームのリプレイを見てデッキを乗り換えたこと。**

我々はデッキを固定変数として扱い最後まで動かさなかった。hosikusa の GA（§2）と
合わせ、**「デッキを設計変数に含める」という分岐に別ルートから2件が到達**している。
我々の対 dragapult 実測 0.341（n=264、フィールドの34.2%）は、この分岐を
取らなかったことの直接の帰結。

### (b) クローンが弱かった理由 — 横断事前学習からの転移

```
彼    10アーキタイプ横断の portfolio モデル（6 epoch, 4.65M decisions）
      → 各デッキの specialist に fine-tune（4 epoch, 1.03M decisions）
我々  各クローンをそのデッキのコーパスだけでゼロから学習
      → 5種すべて操れず（最良 0.5418 対 main 0.7181、同一決定数で top-k 0.5841 対 0.7096）
```

我々は「データ量ではなく表現の問題」までは特定していた（同一決定数での比較）。
**届かなかったのは解法の側＝横断事前学習からの転移。**
Ilia Iliev（§9）も全デッキ1本の BC から入っており、
**マルチデッキ事前学習は上位の共通前提**だったとみられる。

### (c) 探索が効く条件 — value head の出自

> A **BC** value head sees only expert states. Search with a BC value head
> **decreased the score by 20-30 points**.
> A **PPO** value head sees on-policy states. Search with the PPO value head was
> **increasing the score by 50-70 points**.

**我々の探索 A/B が2件とも棄却された理由の説明になる。**模倣由来の価値関数は
熟練者が訪れる盤面しか見ておらず、探索はまさにその外側を評価させるので悪化側に倒れる。

ただし全員一致ではない。同スレッドで:

- **Dipam Chakraborty**: 相手デッキと自分のドローが未知なので MCTS は機能しにくく、
  十分な学習後は素の policy head に対して wash
- **Kh0a**: value head 付き MCTS は 700 で頭打ち、policy head だけは改善し続けた

つまり **PPO の on-policy value を持っているチームだけ探索が効く**、が切り分け。
我々は PPO 側に行けなかった（§8）ので、探索レーンも構造的に閉じていた。

運用条件も具体的: 1決定あたり 60 simulation × 2 回、総エージェント時間 420 秒で打ち切り、
以降は素の policy。起動条件は「選択肢2以上」「selection count 3以下」「エンジンが探索
状態を返す」の3つ。

### (d) スループット工学

190 steps/s → **1400〜4300 steps/s**。相手推論を worker CPU から GPU バッチ呼び出しへ、
**featurizer の numpy スカラー参照を素の Python リストに置換**、検証の並列化。
