# exp083 — スケールアップ BC: 「7分・極小モデル」という投資不足を潰す

## 仮説
exp080 の BC ラダー失敗（0.43）は**容量/表現の壁**と結論していたが、その結論は
**d_model=128 / 1層+1層 / 2ヘッド を合計7分（147秒×3epoch）学習しただけ**の実行から導かれていた。
`pre_grimm10/history.json` の val top-1 は **0.6023 → 0.6121 → 0.624 と最終epochでも上昇中＝未収束**。
＝「BC は無理」ではなく「**BC に投資していなかった**」の可能性。GPU は遊休、教師コーパスは既存。

出典: disc728071（純模倣 ~21k試合で 900-1000 到達・「policy network のスケール」がレバー）、
disc717697（表現が最重要）。提出サイズ上限 197.7 MiB（disc727565）。

## Stage 1: 多層・大規模化への配線（完了）

既存パイプラインは **1層・d128 専用にハードコード**されていた。アーキ族は変えず、その固定を外した。

- `exp041_pilotnet/pretrain.py`: `MyModel(d, 2, d*2, 1, 1)` と固定だったのを
  `--heads / --enc-layers / --dec-layers / --d-ff` で可変化。`--cosine`（長時間学習用のLR減衰）を追加。
  **`arch.json` を results/<tag>/ に書き出す**（ヘッド数は重み形状から復元できないため、以後の
  npnet/eval/ビルドが構成を推測せず再現できるようにする）。per-epoch の `lr` も history に記録。
- `exp041_pilotnet/npnet.py`（numpy推論）: `encoder.layers.0` 直書きだったのを**層ループ化**。
  `mha()/emb_bag()` から module-level の `D/H/HD` 定数を外し、引数化。`infer_arch()` で
  重み名・形状から層数と d_model を復元（heads は arch.json、無ければ legacy=2）。
- **純Python版（`npmcts_policy.py`）は多層化しない**と決定。理由は速度: 実績 0.13s/act（d128,1+1）に対し
  **2.3s/act は実際にラダーでタイムアウト失敗**した（actTimeout≈1s+overage）。d256/2+2 は純Pythonで
  約1.0s/act 相当＝budget 超過なので、多層を純Pythonで走らせる意味がない。
  → **numpy 経路＝大型ネット / 純Python経路＝旧d128 のフォールバック**という二経路構成にする。

### 検証（Stage 1）
- **回帰**: 既存 pre_grimm10（d128/1+1）で `arch={'d_model':128,'heads':2,'enc_layers':1,'dec_layers':1}` を
  自動復元し、torch vs numpy で **n=500, max|dv|=2.97e-08, max|dp|=5.98e-06, argmax 500/500 → PARITY OK**。
  一般化で既存経路を壊していないことを確認。
- **多層**: ランダム初期化 `MyModel(d=64,h=4,ff=128,enc=2,dec=3)` を export→NpNet で
  **arch 完全一致・n=60, max|dp|=2.76e-07, argmax 60/60 → PARITY OK**。多層・非legacyヘッドで動作確認。

## Stage 2: 本気の学習（進行中）

`config.yaml` / `run.sh` に構成を固定（seed 42, opp-drop 0.5=出荷条件, batch 128, cosine LR）。
コーパスは exp080 の 10日分をそのまま再利用（**1,083,793 決定 / 12,235 試合**）＝データ作成コスト0。
検証は **game 単位 held-out**（`is_val(wid, GID)`、train から除外）＝リーク無しを確認済み。

- **A: d_model=256 / heads=4 / enc2+dec2 = 27.2M params**（baseline は 12.8M）、24 epoch、~305秒/epoch。

### A（warmup なし）= 最適化不全で打ち切り
```
ep0 acc 0.4095 / ep1 0.4945 / ep2 0.5856 / ep3 0.5825 / ep4 0.5870
```
ep2 で **0.586 に頭打ちし停滞**、baseline の 0.624 に届かず。ep0 が baseline(0.6023) より大幅に低く
loss も高い（0.1853 vs 0.1667）＝同一データ・同一LRで容量を増やしただけでここまで劣るのは
**容量の問題ではなく最適化不全**（post-norm transformer を warmup 無しで深くした時の既知の挙動）。
→ 打ち切って warmup を導入。

### warmup 導入 = 診断が的中（A2）
`pretrain.py` に `--warmup-steps`（linear ramp）を追加し、**スケジューラを per-epoch から per-batch に
変更**（warmup はステップ粒度が必要なため `train_epoch(sched=...)` で毎バッチ step）。

| | epoch 0 の acc |
|---|---|
| A（warmup なし） | 0.4095 |
| **A2（warmup 4000 step）** | **0.5740** |

**同一アーキ・同一データで +0.165**。原因が最適化だったことが確定した。
（A2 は再起動後も seed 42 で ep0=0.5740 を正確に再現＝決定的で再現性あり）

### だが warmup だけでは足りず、真因は「ピーク LR が高すぎる」（A2 → 探査 → A3）
A2 は ep0 0.5740 → **ep1 0.4896 → ep2 0.5222 と振動**。warmup は ep0 の途中で終わるので、
ep1 以降は**ピーク LR 3e-4 で走る**＝そこが不安定という切り分けになる。
2時間の賭けを繰り返さず、**3 epoch の短い LR 探査**（warmup 後は定数 LR にして「そのピークが安定か」を
直接見る設計）に切り替え、`--clip`（grad-norm クリップ）も追加した。

**探査結果（lr=1e-4 + clip 1.0 + warmup 4000, 定数）**
```
        probe(1e-4)   baseline d128(3epで終了)   A(3e-4,wuなし)   A2(3e-4,wu)
ep0     0.6077        0.6023                     0.4095           0.5740
ep1     0.6255        0.6121                     0.4945           0.4896
ep2     0.6241        0.6240                     0.5856           0.5222
```
**ep1 で baseline の最終値(0.6240)を超え、以後安定**。原因の切り分けが完了した:
- 3e-4 は公式サンプルの値で **d128/1+1 には適切だが d256/2+2 には高すぎる**
- warmup 単独では不十分（ピーク LR 自体が問題）、**warmup + LR 1e-4 + grad clip** で健全化

### A3 = 本番運転（実行中）
上記レシピ + cosine 減衰 24 epoch（探査は定数 LR だったので、減衰分の伸びしろが残っている）。
~307秒/epoch ＝ 合計約2時間。`run.sh A3` にレシピを固定記録。

**A3 結果（24 epoch 完走, 約2時間）**
```
ep0 0.6053 → ep3 0.6438 → ep8 0.6678 → ep13 0.6808 → ep18 0.6888 → ep23 0.6895
最後の6 epoch が 0.688-0.689 で平坦 ＝ 収束済み
```
| | 旧 baseline d128（7分） | **A3 (d256/2+2, 27.2M)** | 差 |
|---|---|---|---|
| top-1 (oracle-free) | 0.6238 | **0.6892** | **+0.065** |
| vs Alakazam (mixed_ex1) | 0.6267 | **0.7059** | **+0.079** |

ラダーでの最大の穴だった **Alakazam 戦の忠実度が最も伸びた**（+0.079、教師例も最多の相手）。

## Stage 4: 二経路ビルド（`build_dual.py`）

`npmcts_policy.py`（純Python net + 特徴量 + agent + クラッシュ安全）に **numpy 高速経路を追記**する方式。
`MODEL` は `.forward()` を持つ単一オブジェクトなので、numpy 版に差し替えるだけで全経路が切り替わる。

- **fast**: numpy + `cg/npnet.npz`（A3, 100.6MB）＋ `cg/arch.json`（ヘッド数は重み形状から復元不能なため必須）
- **fallback**: numpy か npz が使えなければ、**既存の純Python d128 net**（`cg/weights_pure.pkl`）のまま
- import 時に例外を握りつぶす設計＝**numpy が無くても絶対にクラッシュしない**
- 重みは `cg/` 内（配送実績のある経路）、**`__file__` は一切使わない**（v015 の NameError 事故の教訓）

### 検証（Stage 4）
- ビルド: **148.5MB**（上限 197.7MB 内）、top-level = `[deck.csv, main.py]`、必要ファイル全て存在
- parity: A3 の torch vs numpy で **n=500, max|dp|=1.02e-05, argmax 500/500 → PARITY OK**
- 速度: numpy **2.16 ms/decision**（旧 d128 numpy 0.58ms、旧 d128 純Python 130ms）
- **`sandbox_replica.py`（出荷tarのみ・bare exec・`__file__`なしの実harness再現）**:
  - numpy あり → 169手完走、**max_act 0.01s**、total 0.8s
  - **numpy を意図的に遮断** → 110手完走、**max_act 0.19s**（純Python d128 に自動縮退）、クラッシュなし
  → **両経路とも予算内で動作**することを実証。保険が機能する。
- 標準ガントレット・スモーク: **60試合 / 3マッチアップ 0エラー**
  （勝率 0.30/0.25/0.40 は exp007/exp002 の専用パイロット相手＝旧BCネットが同じ相手に 0.000 を出した
   既知のアーティファクト。この種の局所値はラダーを予測しないと今週2度実証済みなので判定に使わない）

## 対照実験（完了）: 伸びは「容量」か「学習量」か — そして出荷可能性の壁
d128/1+1 を**同じ良いレシピ（lr1e-4+clip+warmup+cosine, 24ep）**で再学習（`sc083_d128ctl`, 完走）。

| | 旧 d128（7分） | **d128ctl（2時間）** | A3 d256/2+2（2時間） |
|---|---|---|---|
| top-1 (oracle-free) | 0.6238 | **0.6577** | **0.6892** |
| vs Alakazam | 0.6267 | **0.6745** | **0.7059** |
| 対旧ネット n=200（ゲート2） | — | **0.525 (z=+0.71) FLAT** | 0.665 (z=+4.67) PASS |

**切り分けの結論**: 学習量は top-1 を +0.034 上げるが、**強さには変換されなかった**（0.525＝互角）。
A3 の +0.065 のうち、実際に打ち筋の強さになったのは**容量側**。
＝「純Python の小型モデルで同じ性能」という都合の良い出口は**存在しない**（誠実なネガティブ）。

### これが出荷を塞ぐ
- **出せる構成（numpy不要の d128）はゲート2 に落ちる**（0.525）。事前登録した撤退条件に該当。
  旧 d128 級は実ラダー 0.43 で、koff/alakazam の 0.54 に遠く及ばなかった実績もある。
- **ゲート2 を通る構成（A3 d256/2+2）は出荷できない**。純Python 換算の推定は
  numpy 比（d128 0.58ms → A3 2.16ms ＝ 3.7倍）から **約 0.7s/act**＝ゲート3（≤0.3s）超過、
  かつ v015 が 2.3s/act で実際にタイムアウト失敗した領域に近い。重みも純Python形式で ~110MB。
- ⇒ **ゲート的には出荷根拠が無い**。ビルド自体は `build_pure/`（47.9MB, numpy完全排除,
  torch↔出荷純Python パリティ n=300 argmax 300/300, max|dp|=1.24e-05,
  スモーク120試合0err, sandbox replica 144手 max_act 0.29s）として成立している。

**ユーザー判断: ゲート2 不合格を承知でラダー実測する**として v043 を提出（sub 54988388, **COMPLETE**）。
検証エピソードを通過＝**v042 の原因が numpy 経路/巨大アーティファクトだったことが実地で確認された**
（コードは `npmcts_policy.py` バイト同一、差分は numpy の有無とサイズのみ）。v040 koff(845.4) を退出。

**判定基準（事前登録・変更しない）**: 実ラダー ~40試合の勝率が **koff/alakazam の 0.54 を超えること**。
超えなければ即座に実績ビルドへ復帰し、学習レーンを誠実なネガティブとして再度閉じる。
旧 d128 級は実ラダー 0.43 だった＝**事前確率は低い**ことを明記しておく。

## exp083b: 出口を広げてから容量を増やす（sc083_distil / sc083_deep）

### 純Python 推論の高速化（item 3）— これが全ての前提だった
GPU でどれだけ良いネットを作っても、**出口が 0.29s/act で埋まっていれば出せない**。
プロファイルすると `_linear` が **全体の88%**（7.48s / 8.51s）。フラット配列を Python レベルで
1要素ずつ添字アクセスしていたのが原因。**重み行列をロード時に出力行ごとの `array.array` に分割**し、
内積を `sum(map(mul, x, row))`（C 側で完結）に変更。

| | 変更前 | 変更後 |
|---|---|---|
| ms/decision | 126.2 | **68.9** |
| max_act | 0.29s | **0.15s** |

併せて **N層・任意ヘッド数に一般化**（層数=重み名、d_model/d_ff=形状から復元。ヘッド数だけは
復元不能なので `arch.json` 必須）。検証: 既存 d128/1+1 回帰 **300/300**（値も変更前と同一）、
ランダム `d64/h4/enc2+dec3` を実出荷パイプライン経由で **60/60**。

### 蒸留（item 1）— ラベルを柔らかくすると、同じ容量でも強くなる
`d128ctl` の失敗は「人間ラベルの top-1 を当てる能力」は伸びたが打ち筋にならなかったこと。
ハードラベルは**選ばれた1手しか教えない**が、教師は**残り全候補の良し悪し**も教える。
`--teacher/--distill` を追加し、A3 の出力ベクトルを重み0.7でターゲットに混ぜた。

### 層で容量を増やす（sc083_deep）— サイズと計算量の非対称性を突く
**サイズは埋め込み（vocab × d_model）が支配し、計算量は層が支配する**。よって d_model=128 を
据え置いて enc2+dec2 にすれば、**ファイルは ~51MB の実績圏のまま**容量だけ増やせる。
計算量2倍は item 3 の貯金で吸収。**これは item 3 が終わるまで実行不可能な構成だった**。

### 結果

| | top-1 | vs Alakazam | ゲート2 |
|---|---|---|---|
| 旧 d128（7分） | 0.6238 | 0.6267 | — |
| d128ctl（ハードラベル・2h）＝**v043** | 0.6577 | 0.6745 | vs旧 0.525 (z=+0.71) |
| distil（d128 1+1） | 0.6820 | 0.6985 | vs d128ctl **0.573 (z=+2.90)** |
| **deep（d128 h4 2+2）** | **0.6967** | **0.7129** | vs distil 0.545 (z=+1.80) |
| A3 教師（d256 2+2、**出荷不能**） | 0.6892 | 0.7059 | vs旧 0.665 (z=+4.67) |

**deep vs d128ctl（＝ラダー上の v043）: 0.635 (254-141-5, z=+5.40, n=400)**。
3つの改善（学習レシピ・蒸留・層追加）が各々小さく積み上がった結果で、**どれ1つでも届かなかった**。
deep は top-1 でも教師 A3 を超えた（生徒が教師を超えるのは蒸留では珍しくない＝ソフトターゲットの正則化効果）。

### ビルド検証と**ゲート3 の明示的な改訂**
- 48.9MB / パリティ **300/300**(max|dp|=2.49e-06) / arch.json 同梱（heads=4）
- **`arch.json` 未同梱は静かな誤動作**: ヘッド数は形状から復元できないので、無ければ純Python 側は
  既定の2ヘッドで動き、**クラッシュもエラーも出さずに別の関数になる**。
  `build_np_submission.py` に同梱と一致 assert を追加した。
- **max_act = 0.35s ＝ 事前登録した ≤0.3s を超過**。

**ゲート3 を「max_act ≤0.5s かつ 1試合合計 ≤60秒」に改訂した**（ユーザー承認済み）。
理由は「超えたから緩める」ではなく、**0.3s が実績2点（0.13s 通過 / 2.3s 失敗）から置いた代理値に
すぎず、直接の制約を測り直したから**:
- 1試合 **28.5秒（両席）＝1席 ~14秒**、overage bank **600秒**に対し消費 2.4%
- 試合上限は10分。桁が違う
- コード内蔵の安全弁は **1.5秒/手 × 3回でネットを自動切断**＝0.35s はその1/4
- 実運用中の v043 は max_act 0.29s でタイムアウトゼロ

## exp083c: 「模倣が見ている情報」そのものを疑う（v044 提出）

ユーザーの2つの指摘が起点。どちらも当たっていて、片方は想定より深刻だった。

### 指摘1: ±1 回帰は過信ではないか（引いた札からしか選べない以上、観測手＝最善手ではない）
正しい。ただし**負例を完全にマスクすると退化する**（対比が消え、全候補 +1 が最適解になり argmax が無意味になる）。
成立する形として3つ実装（`--policy-loss {huber,margin,ce}`）:
- **margin**（採用）: 観測手より**上に位置する候補だけ**を罰す。下にあるものは損失ゼロ＝「判断できないものは
  supervise しない」を、対比を保ったまま表現できる。ユーザー案に最も忠実。
- **ce**: softmax 交差エントロピー + label smoothing。対比は正規化で作る。
- 方向の妥当性は蒸留で既に実証済みだった（負例を柔らかくする操作＝distil が d128ctl に 0.573, z=+2.90）。

### 指摘2: 実際にポケカで参照する情報を漏れなく入れているか
**入っていなかった。しかも最も基本的なものが。** エンジンが観測として出しているのに**使用回数ゼロ**:

| 区分 | 欠落していたフィールド |
|---|---|
| ターン内資源 | `supporterPlayed` `energyAttached` `stadiumPlayed` `retreated` `turnActionCount` |
| ポケモン | `maxHp`（KO距離）`appearThisTurn`（進化可否）`preEvolution` `energies`（型） |
| プレイヤー | `benchMax` 表向きサイド |

### 発見: 価値ヘッドは「工夫の余地」でなく**動いていなかった**
出荷ネットの価値出力を実局面300で測定: **min 0.99986 / max 1.00000 / stdev 0.00002 ＝ 定数**。
原因は `scan_teachers.py` の「we imitate winning play」＝**勝った試合だけを集めていた**こと。
outcome ラベルが全レコード +1 なので、価値ヘッドは「常に1を出せ」と学習していた。

**これが過去の重要なネガティブを無効化する**: 学習レーンを閉じた根拠の1つ
「MCTS レバー = 0.300 (z=-3.10)＝探索は逆効果、価値関数が中盤を読めない」は、
**価値関数が定数だった条件下**の測定だった。定数を評価関数にした探索はノイズを撒くだけ。

### 提出（v044, ユーザー承認済み）
eligible = **{v043 545.8, v044}**。**v041 alakazam 773.6 を退出**（816.8→802→792→773.6 と低下継続中だった）。
枠の算術上、新規提出は常に最古＝alakazam を押し出すため、v043 の死に枠は温存される。
**段階戦略**: ~40試合で v044 を評価 → 良ければ2枚目を出して v043 を押し出し独立2ドロー、
悪ければ実績ビルドへ復帰。**v044 が 773.6 を超えるまでは名目上の後退**であり、それが引き受けたリスク。

### 次の一手（枠コスト0の候補）
A3 の利得が「埋め込み幅」か「層の深さ」かをもう一段分ける。**計算コストは層に、サイズは埋め込みに**
偏っている（27.2M のうち大半は vocab×d の EmbeddingBag、行列演算は層側）ので、
**d128 のまま enc2+dec2** なら**ファイルは ~51MB の実績圏のまま**で容量だけ増やせる。
純Python の実行コストは約2倍（max_act 0.19s → ~0.4s）でゲート3 ぎりぎり＝
純Python NpNet の多層化と高速化がセットで必要。これが通れば出荷可能な形で A3 の利得に近づく。

## 判定原則（重要）
**local eval はラダーを予測しない**（pub1034 BC ゲート・dragapult で2度実証、[[local-not-ladder]]）。

出荷根拠にしない。出荷判定は**実ラダー ~40試合の勝率が koff/alakazam の 0.54 を超えるか**のみ。
