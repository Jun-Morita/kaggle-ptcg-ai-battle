# exp085 — GBDT オプション・ランカー

## 仮説

transformer BC は 16件の誠実なネガティブを積んで止まっている。ローカルで区別できず、
ラダーでは退行する（28日コーパスが約70点、gate_field は FLAT と判定）。

公開ノートブック tetsutani（`grimmsnarl-ex-damage-transfer-control`, 08-04 時点 864.4）は
まったく別の学習器で同程度に到達している。中核は**勾配ブースティング決定木のアンサンブル**で、
選択肢1つずつを平坦な特徴量の行にして採点し、上位 k 個を取る。約1,300木・180KB・探索なし・
純Python推論。手書きガードはその上に多段の上書きとして乗る。

仮説: この規模のデータでは、系列モデルより**選択肢ランキング**の方が分散が小さく、
特徴量に名前があるので誤りを特定して直せる。

**模倣したのは問題の形（選択肢を明示的な特徴量でランク付けする）だけ。**
コードも重みも取り込んでいない。特徴量は engine API から自前で設計した。

## 構成

```
feats.py            309特徴量／選択肢1行
build_rows.py       教師リプレイ → 行 + 0/1ラベル、qid でクエリを区切る
train_gbdt.py       LambdaRank、SelectContext を5系統に分けて別モデル
export_pure.py      LightGBM → 純Python木テーブル（numpy不要）
parity_pure.py      LightGBM と純Python版の一致検証
gbdt_policy.py      エージェント本体。フォールバック回数を数える
build_submission.py tar 組み立て（main.py に feats/policy を連結）＋実artifactスモーク
eval_h2h.py         harness.run_gauntlet での対戦。--artifact で出荷tarを直接測る
diag_errors.py      誤りを context / OptionType / カード別に分解
```

## 誠実なネガティブと、その原因

### v2 — アーキタイプ・ラベルで作ったコーパスは別デッキだった

40万決定を 07-01〜07-11 から作ったところ、教師再現は 0.684 → **0.798** に上がったのに
強さは落ちた。原因はコーパスで、**我々の60枚は 07-17 以前のメタに存在しない**。

| 期間 | 教師の60枚が我々と完全一致する割合 |
|---|---:|
| 07-01〜07-09 | 0.00 |
| 07-10〜07-16 | 0.00〜0.14 |
| 07-17〜07-23 | 0.33〜0.57 |
| 07-24〜07-28 | 0.55〜0.73 |
| 全体 | 0.233 |

`mixed_ex3` というアーキタイプ・ラベルは同じでも中身は別構築。**持っていないカードのプレイを
忠実に覚えた**ため、忠実度が上がって強さが下がった。v3 は 60枚完全一致だけを使い、
14,392シートを除外している。

**transformer 側の28日コーパス（v048、ラダーで約70点の劣化、ローカルゲートは FLAT）も
同じ作り方**なので、同一原因である可能性が高い。

### 静かに劣化する不具合を3件（すべてエラー0件で通過していた）

| 箇所 | 症状 | 見え方 |
|---|---|---|
| `load_ref.py` | 参照エージェントの lazy import 失敗 | 196決定中115で適当な合法手。3-117 で「我々が圧勝」に見えた |
| `feats.py` | `train_mcts` import 失敗（サンドボックスに無い） | 全カードIDが 0。出荷tarが 0.150/0.000/0.100 |
| `build_submission.py` | 連結時に `feats.option_rows` の参照が解決不能 | **全判断がフォールバック**。0勝25敗×3、`err0=0`、スモークは「OK」 |

いずれも例外を握り潰して**合法だが無意味な手**を返す形。クラッシュしないので気づけない。
対策として `gbdt_policy` にフォールバック回数のカウンタを入れ、スモークで 0 を要求するようにした。

### 自前の評価ループが壊れていた

`eval_gbdt.py`（当日書いた自前ループ）は `harness._validate_selection` を通さず、
デッキと席を手で割り当てていた。同じモデルで自前ループ 0.480、`run_gauntlet` 0.120。
**今日の GBDT 対戦数値のうち、`eval_gbdt.py` 由来のものはすべて破棄した。**

物差しの検証を `--defer all`（ミラー戦）で済ませたのが誤り。**両席が同じデッキなので
デッキと席の取り違えは原理的に見えない。**7月末にも同型の失敗（ミラー限定ゲート）をしている。

以後の対戦はすべて `harness.run_gauntlet` ＋ `--artifact`（出荷tar直接）で測る。

### 記事から取り込んだ設計（invenglobal 24133, DeNA / Pokémon TCG Pocket）

| 記事 | 我々の対応 |
|---|---|
| 行動を原子単位に分解して行動空間の爆発を避ける | 選択肢の独立採点＋上位k。現行 MCTS の組み合わせ列挙とは逆 |
| 単一行動局面は学習データから除外 | 実装済み（v3 で 53,678決定を除外） |
| 誤用はカードへの罰でなく**補助特徴量**で直す（正用率 96.2%） | 下記 |

`diag_errors.py` が v1 で一貫した偏りを検出した:
ABILITY 603 / EVOLVE 404 を過剰に上位へ、ATTACK 220 / RETREAT 101 / END 57 を過剰に落とす
＝「何かをやり続けて、攻撃・撤退・ターン終了をしない」。
特徴量に**技のダメージ値が一切なかった**（`opt_attack_id` から暗記するしかない）。
`opt_attack_damage / energy / lethal / margin` と局面側13個を追加（292→309）。
ATTACK の扱いは落とし220:上げ109（2:1）→ 落とし524:上げ586（ほぼ均衡）に変化した。
