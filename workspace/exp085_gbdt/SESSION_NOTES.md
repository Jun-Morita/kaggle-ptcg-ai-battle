# exp085 — GBDT オプション・ランカー

## 仮説

transformer BC は 16件の誠実なネガティブを積んで止まっている。ローカルで区別できず、
ラダーでは退行する（28日コーパスが約70点、gate_field は FLAT と判定）。

公開ノートブック tetsutani（`grimmsnarl-ex-damage-transfer-control`, 08-04 時点 864.4）は
まったく別の学習器で同程度に到達している。中核は**勾配ブースティング決定木のアンサンブル**で、
選択肢1つずつを平坦な特徴量の行にして採点し、上位 k 個を取る。約1,300木・180KB・探索なし・
純Python推論。手書きガードはその上に多段の上書きとして乗る。

仮説: この規模のデータでは、系列モデルより**選択肢ランキング**の方が分散が小さく、
特徴量に名前があるので誤りを特定して直せる。

**模倣したのは問題の形（選択肢を明示的な特徴量でランク付けする）だけ。**
コードも重みも取り込んでいない。特徴量は engine API から自前で設計した。

## 誠実なネガティブと、その原因

### v2 — アーキタイプ・ラベルで作ったコーパスは別デッキだった

40万決定を 07-01〜07-11 から作ったところ、教師再現は 0.684 → **0.798** に上がったのに
強さは落ちた。原因はコーパスで、**我々の60枚は 07-17 以前のメタに存在しない**。

| 期間 | 教師の60枚が我々と完全一致する割合 |
|---|---:|
| 07-01〜07-09 | 0.00 |
| 07-10〜07-16 | 0.00〜0.14 |
| 07-17〜07-23 | 0.33〜0.57 |
| 07-24〜07-28 | 0.55〜0.73 |
| 全体 | 0.233 |

`mixed_ex3` というアーキタイプ・ラベルは同じでも中身は別構築。**持っていないカードのプレイを
忠実に覚えた**ため、忠実度が上がって強さが下がった。v3 は 60枚完全一致だけを使い、
14,392シートを除外している。

**transformer 側の28日コーパス（v048、ラダーで約70点の劣化、ローカルゲートは FLAT）も
同じ作り方**なので、同一原因である可能性が高い。

### 特徴量 309 → 318（誤り診断ループ 2周目）

v3 の held-out 誤り 0.262（MAIN 52.3% + TO_HAND 21.7% で全体の74%）。
v2 で足した攻撃ダメージでも解消しない偏りが残っていた:

| OptionType | 誤って上位に | 誤って落とす | 比 |
|---|---:|---:|---|
| ABILITY | 2413 | 1655 | 1.46 : 1 |
| EVOLVE | 966 | 652 | 1.48 : 1 |
| ATTACK | 351 | 678 | 1 : 1.93 |
| RETREAT | 99 | 261 | 1 : 2.64 |
| END | 36 | 160 | 1 : 4.44 |

誤って上位に入れたカードの1位は **Munkidori（ダメカン移動の特性）で 2,888件**。

原因: **モデルは「このターンに既に何回使ったか」を見られない。** prev1..3 は直前3手までなので、
ターンの8手目を決める時点で「もう2回動かした」と「まだ何もしていない」が区別できない。

追加:
`turn_actions_so_far` / `turn_abilities_used` / `turn_plays_used` / `turn_attaches_used` /
`turn_evolves_used` / `opt_src_acted_this_turn` / `opt_same_action_this_turn` /
`opt_counters_to_ko` / `opt_tgt_hp_ratio`

履歴の持ち方を `(turn, semantic)` に変更し、窓を 3 → 40 に拡張（1ターンが十数手になるため）。

**作業中に見つけた2件:**

1. ダメカン系の対象解決が `inPlayArea` 経由だけだった。DAMAGE_COUNTER 文脈は
   `area` + `playerIndex` で対象を指すため、**追加した特徴量が全て 0** だった。
   `semantic()` と同じフォールバックを入れて修正（785行で発火するようになった）。
2. `remainDamageCounter` はリプレイ観測では**常に 0**。これを使う「カウンターが足りるか」の
   フラグは一度も発火しないので、木が自力で作れない比率（対象の残HP割合）に差し替えた。

### 探索: 検証付き上書き（`search.py`）

MCTS を全面移植せず、**v013 の upside-only gate / v014 の turn-beam と同じ設計**を採った。

```
1. GBDT で全選択肢を採点し、上位M個の候補手を作る（部分集合の全列挙はしない）
2. 各候補を determinize したエンジンで適用し、自ターンが終わるまで GBDT で貪欲に打ち切る
3. 到達局面を価値モデルで評価する
4. 方策の第1候補を MARGIN 以上上回るときだけ上書きする
```

`determinize` は exp040 の実装を使う（`npmcts_policy.py` に純Python移植版が既にあり、
現行提出で動いているので出荷経路も確保済み）。

選択の理由: MCTS は実装面積が大きく、**この実験だけで静かに劣化する不具合が3件**出ている。
方策を主役に置き先読みを確認にだけ使う設計なら、壊れても方策の答えに戻る。

動作確認: **26ミリ秒/決定**（1試合600秒の予算に対して桁違いに軽い）。

### 価値モデル（`build_value.py` / `train_value.py`）

探索には局面評価が要るが、既存コーパスは**勝者のみ**で学習信号が無い。両席を取る
コーパスを新設した。ロールアウトではなく学習モデルを選んだのは速度: ロールアウトは
1回0.2秒で1手25回程度しか回せないが、決定木なら数マイクロ秒で3桁多く評価できる。

**学習分布の偏り（記録）:**
- 負けの行は**ミラー戦に偏る**。両席が我々のデッキを持つのはミラーだけなので、
  「我々のデッキが Alakazam に負ける」局面はラダーより大幅に少ない。
- ラベルは最終結果なので、**強いパイロットが打ち切った互角局面も 1** になる。
  探索は兄弟局面の順序さえ合えば良いので単調変形には耐えるが、絶対値は勝率ではない。

### 測定の方針

**変更は一度に1つずつ測る。** v2 でコーパスと特徴量を同時に変えて切り分け不能にした反省。

1. v4 学習 → 出荷tarで対 v3（318特徴量の効果を単独で測る）
2. 価値モデル学習 → 同一モデルで探索あり vs なし

## 探索 — 誠実なネガティブ（8/7、レーンを閉じた）

`search.py`（検証付き上書き）＋ 価値モデル（80万行、AUC 0.9086）で A/B を2回:

| 上書き閾値 | n | 探索なし | 探索あり | 差 | 上書き率 |
|---|---:|---:|---:|---:|---:|
| 0.02 | 60 | 0.567 | 0.467 | -0.100 (z -1.10) | 10.8% |
| 0.12 | 120 | 0.608 | 0.542 | -0.067 (z -1.03) | 5.1% |

個々は有意でないが**符号が一致**しており、閾値を上げて上書きを半減させても改善しない
＝上書きが多すぎるのではなく、**上書きの選び方が良くない**。

原因の見立ては価値モデル。AUC 0.9086 は全局面の数字で終盤が簡単なだけで、探索が要求する
**同一ターン内の兄弟局面**の順序は捉えられていない。学習分布の偏り（負けの行がミラー戦に
偏る、互角局面も勝ちラベル）もこの用途では効く。正しく直すには価値の学習方法を変える必要が
あり（局面の優劣を直接学ぶ、自己対戦で作る）、残り9日では合わないと判断。

**速度は問題なかった**（軽い設定で平均22ms/決定、1試合1.9秒）。最初に報告した「38秒/手」は
重い設定（determinize 2回・24手先読み）での単発値。

### 符号バグ（記録）

初回測定は **0.015（3-197）**。原因は `search.py` に自分で書いたコメントの通りの反転を
実装していなかったこと。`_greedy_finish` は自ターン終了時点で止まるので評価対象は相手の
手番であり、`base_state` は手番側視点なので、探索は**相手の勝率を最大化する手**を選んでいた。
`value_of(oc, our_index)` に署名を変え、手番が自分でなければ 1-v を返すよう修正。

この実験で4件目の「静かに劣化する不具合」だが、前3件と違い**大きく壊れたので即座に分かった**。
危険なのはもっともらしい数字を出す壊れ方の方。

## 08-08 v6: コーパス上限の撤廃とサーチ特徴（v054 として提出）

### 仮説

1. `--max-dec 700000` は計算都合の打ち切りで、教師 seat の4割強を捨てている。

### 変更

コーパス: 700,012 → **1,188,672 決定**（1.70倍）。

`feats.py` に10特徴（318→336、**末尾に追加**したので旧318列は不変）:

## 08-09 教師をラダースコアで絞る（v055 として提出）

### 仮説

教師インデックスにラダースコアが入っていた（`['88529412.json', 0, 'mixed_ex3', 1142.3]`）。
すでに 1000点以上に絞られていて、seat の分布は p50 1069 / p90 1142 / 上限 ~1170。
上位の教師だけを使えば模倣の天井が上がるのではないか。ただし v6 で量が効いたことは
確認済みなので、質はデータ損失に勝たなければならない。

### 実装

閾値ごとにコーパスを作り直すと1回2時間かかる。そこで **行と一緒に教師スコアを
書き出し、学習時に `--min-score` で切る** 形にした。

- `build_rows.py` が5要素チャンク `(ctx, qid, y, X, score)` を書く
- `train_gbdt.load_family` が `min_score` で絞る
- 旧4要素チャンクは0埋めで読めるので、古いコーパスも壊れない

行レベルの残存率は seat ベースより高い。上位の教師ほど1試合あたりの決定数が多い。

```

>= 1100   46.5% of rows
>= 1150   15.3% of rows
```
